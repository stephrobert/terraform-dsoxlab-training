# Scenario: reconcile a drift and adopt an orphan resource

**Target exam sub-objective: 1e.**

A colleague edited a file by hand and left behind a value created outside
Terraform. This lab tackles the trap the guide leaves open: believing that
`plan -detailed-exitcode` detects drift, when it merely signals a non-empty diff.
The reliable drift detector is `plan -refresh-only`.

## Target capability

Diagnose a drift with a saved refresh-only plan, reconcile it explicitly, then
adopt a pre-existing resource into the state without triggering its replacement
at the next apply.

## Where the learner starts

`main.tf` is complete and ready to apply: the `terraform` block and the
`local_file.note` resource, which writes `data/note.txt`. A second file,
`adoption.tf`, carries the adoption to come, **shipped commented out** so that
the configuration applies as is: the `random_string.legacy` resource with its
holed `lifecycle` block, and the `import` block whose `to` and `id` are `???`.
Uncommented too early, that file would **create** a random token instead of
adopting the existing one.

The `token-herite.txt` fixture holds the string created outside Terraform, known
to a third-party service: nobody can regenerate it, it must be adopted as is.

No `terraform.tfstate` exists at the start. The statement has the learner build
the reference state (`init` then `apply`), then cause the incident by overwriting
`data/note.txt` by hand. The drift is therefore real, not prefabricated.

## The state to reach

1. A refresh-only plan, saved then **converted**, as `derive-plan.json`, carrying
   at least one `resource_drift` entry for `local_file.note` and whose
   `resource_changes` is **empty**: the signature of a refresh-only plan, an
   ordinary plan storing the same information **in both** lists. The conversion
   (`terraform show -json derive.tfplan > derive-plan.json`) is not cosmetic: a
   plan file is a **binary**, unreadable by tests as by a reviewer.
2. The state describes only what really exists:
   `terraform plan -refresh-only -detailed-exitcode` exits **0**.
3. `data/note.txt` is back to the content declared in `main.tf`, and
   `local_file.note` is in the state again, in `mode: managed`.
4. `random_string.legacy` is in the state in `mode: managed`, its `result`
   attribute holding **exactly** the string from `token-herite.txt`. A value
   regenerated by a plain apply cannot match by chance.
5. No replacement pending on the adopted resource:
   `terraform plan -detailed-exitcode` exits **0**. The declared `length` (24,
   team policy for every new token) does not match the inherited token (16
   characters): without `lifecycle { ignore_changes = all }`, the plan announces
   `must be replaced` under the warning `Warning: this will destroy the imported
   resource`, and the apply **regenerates** the value. Both exit codes are **0 at
   the same time**: the state matches the real world, and the real world matches
   the code.

## How it is proven

Tests run Terraform inside `challenge/work` and never read the `.tf`.

- `derive-plan.json` is read back as a plan document: the test requires the
  `format_version` field, a `resource_drift` entry for `local_file.note`, and an
  **empty** `resource_changes`. A converted ordinary plan fails on that last
  point.
- `terraform show -json`: the test walks `values.root_module.resources`, requires
  both addresses in `mode: managed`, compares `random_string.legacy.result` with
  the content of `token-herite.txt`, and the real content of `data/note.txt` with
  the `content` the state attributes to `local_file.note`.
- `terraform plan -detailed-exitcode` and its `-refresh-only` variant, both run
  with `-input=false`, must return `0`; the test fails on `2` and tells the two
  causes apart in its message.
