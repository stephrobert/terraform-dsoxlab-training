# Scenario: prove that Terraform has a memory

**Exam sub-objective covered: 1e (state, import, drift).**

A beginner believes Terraform re-reads the `.tf` files and queries the infrastructure on every command, the state being an accessory cache. This lab takes that idea apart: without a mapping stored in the state there is no empty plan, no drift detection, and no stable identity for resources that already exist.

## Target capability

Establish, on a purely local configuration, that the state is what ties the code to reality: show that a second apply produces no change, that drift caused outside Terraform is detected then repaired without losing the identity of the untouched resources, that data merely read is not a managed resource, and that an object nobody declared stays invisible to the tool.

## Where the learner starts

The `challenge/work` directory contains:

- `versions.tf`: complete, it pins the `random`, `local` and `null` providers.
- `main.tf`: full of holes. The `random_pet` length, then the `content` and the
  `filename` of the `local_file`, are `???`. The content must be built from the
  identifier produced by `random_pet`, never pasted by hand: that reference is
  what creates the dependency. A `local_file` data source reading
  `inventaire.txt` is also to be completed.
- `outputs.tf`: full of holes. Three outputs, the generated name, the report
  path, and one declared sensitive, derived from the name.
- `inventaire.txt`: a hand-written file nobody declared as a resource. It serves
  as both witness and target for the data source.

Nothing is initialised: no `.terraform/`, no lock file, no state.

## The state to reach

1. The providers are installed and the lock file lists `random`, `local` and
   `null` with resolved versions.
2. The state holds exactly two resources in managed mode, one `random_pet` and
   one `local_file`, and no other.
3. The state holds one entry in data mode pointing at `inventaire.txt`: it is
   distinct from the managed objects and its disappearance would destroy nothing
   on disk.
4. The report exists on disk and its content carries the exact identifier
   generated by `random_pet`: it was therefore produced by Terraform, not typed.
5. The sensitive output exists, its value is not revealed by the usual display
   but appears in the clear in the state: the state is itself sensitive data.
6. A new apply produces no change: configuration, state and disk are aligned.
7. If the report is deleted outside Terraform, drift is detected: a single
   resource is to be recreated, and the `random_pet` identifier survives intact.
8. The state file was never hand-edited.

## How it is proven

The tests never open the learner's `.tf` files and never read Terraform's human-facing output to derive a state from it.

- `terraform show -json` provides the state. The tests count entries by mode
  (`managed` against `data`), check the expected types and pick up the
  `random_pet` identifier from its attributes.
- `terraform output -json` gives the name and the path, and proves the
  `"sensitive": true` marking on the third output. The tests open the file the
  path points at and require the identifier taken from the state to appear in it.
- `terraform plan -detailed-exitcode` must return code 0: a formal proof of
  idempotence, without interpreting a line of text.
- For drift, the tests copy the working directory with its state into a
  temporary folder, delete the report there, produce a plan converted to JSON,
  and check in `resource_changes` that a single create targets the `local_file`
  while the `random_pet` stays unchanged. The learner's work is never modified.
- Finally, no managed address may reference `inventaire.txt`.
